## 📝 IMPORTANT SHORT ANSWERS (5-Mark Style)

### Social Engineering Attack Cycle
1. **Information Gathering** - Research target (OSINT, social media, dumpster diving)
2. **Relationship Development** - Build trust, establish rapport
3. **Exploitation** - Manipulate to reveal info/perform action
4. **Execution** - Use obtained info for attack
5. **Exit** - Cover tracks, avoid detection

### SQL Injection Example
```
Vulnerable Query: SELECT * FROM users WHERE username = 'input' AND password = 'pass'
Attack Input: ' OR '1'='1' --
Result: SELECT * FROM users WHERE username = '' OR '1'='1' -- ' AND password = 'pass'
→ Bypasses authentication, logs in as first user
```
**Prevention**: Parameterized queries, input validation, least privilege DB accounts, WAF

### XSS vs XSRF
| Aspect | XSS (Cross-Site Scripting) | XSRF (Cross-Site Request Forgery) |
|--------|---------------------------|-----------------------------------|
| **Mechanism** | Inject malicious script into trusted site | Trick user into submitting forged request |
| **Target** | User's browser executes attacker's script | User's authenticated session |
| **Types** | Stored, Reflected, DOM-based | GET-based, POST-based |
| **Prevention** | Input validation, output encoding, CSP | Anti-CSRF tokens, SameSite cookies, referer check |

### ER Model Components
- **Entity**: Real-world object (e.g., Student)
- **Attribute**: Property of entity (e.g., RollNo, Name)
- **Relationship**: Association between entities (e.g., Student *Enrolls* Course)
- **Cardinality**: One-to-One, One-to-Many, Many-to-Many

### Database Concurrency Control Methods
1. **Locking Protocols** - Shared (read), Exclusive (write), Two-Phase Locking (2PL)
2. **Timestamp Ordering** - Assign timestamps, serialize by TS
3. **Optimistic/Validation** - Validate at commit time
4. **Multiversion Concurrency Control (MVCC)** - Multiple versions

**Goals**: Serializability, Recoverability, Isolation, Deadlock prevention

### Shadow Paging Recovery
- Maintain **two page tables**: Current (modified) and Shadow (original)
- On transaction commit: Switch pointer to current → shadow
- On crash: Shadow page table has consistent state
- **Advantage**: No log needed, fast recovery
- **Disadvantage**: Fragmentation, overhead of page table copy

### Extended vs Base Services of Server Programs
| Base Services | Extended Services |
|--------------|-------------------|
| Process management | Load balancing |
| Memory management | Failover/High availability |
| File system access | Clustering |
| I/O management | Session management |
| Network communication | Caching |
| Security (auth/access) | Transaction management |

### VAPT Steps
1. **Planning & Scope Definition** - Rules of engagement, targets
2. **Information Gathering** - Passive/active reconnaissance
3. **Vulnerability Scanning** - Automated tools (Nessus, OpenVAS)
4. **Vulnerability Analysis** - Verify, categorize (CVSS)
5. **Exploitation/Penetration Testing** - Controlled exploitation
6. **Post-Exploitation** - Privilege escalation, lateral movement
7. **Reporting** - Findings, risk rating, remediation
8. **Re-testing** - Verify fixes

### Ransomware Lifecycle
1. **Delivery** - Phishing, exploit kits, RDP brute force
2. **Installation** - Persistence via registry, services
3. **Command & Control** - Connect to C2 server
4. **Discovery** - Network enumeration, file search
5. **Lateral Movement** - Spread via SMB, credentials
6. **Encryption** - Encrypt files (AES+RSA), delete shadows
7. **Ransom Demand** - Note with payment instructions
8. **Exit** - Self-destruct, cover tracks

**Prevention**: Backups (offline), patching, EDR, network segmentation, user training, MFA

### Zero-Day Vulnerability
- **Definition**: Unknown to vendor, no patch exists, actively exploited
- **Significance**: High value to attackers, bypasses signature-based defenses
- **Recent Examples**: Log4Shell (CVE-2021-44228), PrintNightmare, ProxyLogon (Exchange)
- **Defense**: Behavior-based detection, threat intelligence, patch management, network segmentation

### Kerberos Authentication Steps
1. **AS Request** → Client → AS: User ID
2. **AS Reply** → AS → Client: TGT (encrypted with TGS key) + Session Key (encrypted with user key)
3. **TGS Request** → Client → TGS: TGT + Service ID + Authenticator
4. **TGS Reply** → TGS → Client: Service Ticket (encrypted with service key) + Service Session Key
5. **AP Request** → Client → Service: Service Ticket + Authenticator
6. **AP Reply** → Service → Client: Mutual authentication confirmation

### MITM Attack Techniques
- **ARP Spoofing** - Poison ARP cache, intercept LAN traffic
- **DNS Spoofing** - Redirect to malicious server
- **SSL Stripping** - Downgrade HTTPS to HTTP
- **WiFi Eavesdropping** - Rogue AP, packet sniffing
- **BGP Hijacking** - Redirect internet traffic
- **Session Hijacking** - Steal session cookies

### 1. Extended & Base Services of Server Programs (ASKED 3 TIMES EXACTLY)

**Base Services** (Core OS services provided to server programs):

### 3. Database Concurrency Control (ASKED 2 TIMES)

**Problem**: Concurrent transactions cause Lost Update, Dirty Read, Non-repeatable Read, Phantom Read

**Methods**:
1. **Lock-Based (Pessimistic)**
   - Shared (S) locks for read, Exclusive (X) for write
   - **Two-Phase Locking (2PL)**: Growing phase (acquire), Shrinking phase (release)
   - **Strict 2PL**: Hold X-locks till commit
   - Deadlock handling: Prevention (ordering), Detection (wait-for graph), Timeout

2. **Timestamp-Based**
   - Each transaction gets unique TS at start
   - Read/Write timestamp on each data item
   - Reject if conflict violates serializability

3. **Optimistic/Validation**
   - Read phase: No locks, track read/write sets
   - Validation phase: Check conflicts before commit
   - Write phase: Apply changes
   - Best for low-conflict environments

4. **Multiversion (MVCC)**
   - Maintain multiple versions of data
   - Readers don't block writers, writers don't block readers
   - Used in PostgreSQL, Oracle, MySQL InnoDB

**Goals of Concurrency Control**:
- **Serializability**: Equivalent to some serial execution
- **Recoverability**: Committed transactions survive crashes
- **Cascadeless**: No cascading rollbacks
- **Deadlock Freedom**: System doesn't deadlock
- **Performance**: Maximize throughput, minimize latency

### 5. Three-Tier vs Two-Tier Client-Server Architecture

**Two-Tier**:
```
Client (Presentation + Business Logic) ↔ Database Server
```
- Fat client, business logic on client
- Tight coupling, poor scalability
- Security risk (DB credentials on client)

**Three-Tier**:
```
Client (Presentation) ↔ Application Server (Business Logic) ↔ Database Server
```
- Thin client, logic centralized
- Better scalability (scale app server independently)
- Improved security (DB not exposed to clients)
- Reusability, maintainability, flexibility

### 6. PKI Architecture & Working

**Components**:
- **CA (Certificate Authority)**: Issues, signs, revokes certificates
- **RA (Registration Authority)**: Verifies identity before CA issues cert
- **Certificate Repository**: Stores certificates (LDAP/Database)
- **CRL/OCSP**: Certificate Revocation List / Online Certificate Status Protocol
- **Key Pair**: Public (in cert) + Private (kept secret)

**Certificate Fields**: Version, Serial Number, Signature Algorithm, Issuer, Validity Period, Subject, Subject Public Key Info, Extensions (Key Usage, SAN, Basic Constraints)

**Working**:
1. User generates key pair, sends CSR to RA
2. RA verifies identity, forwards to CA
3. CA signs certificate with its private key
4. Certificate distributed to repository
5. Parties verify cert chain to trusted root CA
6. Check revocation via CRL/OCSP
7. Use public key for encryption/signature verification
